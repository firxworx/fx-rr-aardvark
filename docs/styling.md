# Styling

The palette tokens, animations, and variants of both [coss-ui](https://coss.com/ui/docs) and [shadcn/ui](https://ui.shadcn.com/) are supported in the tailwind configuration.

For consistent styling with minimum effort it is best to choose one of the two registries as the "preferred" set for a project and use the other in special cases or to cover gaps.

## Global Styles

Global styles live in the `@workspace/ui` package under `packages/ui/src/styles`.

`globals.css` is the global style entrypoint to be imported by applications including `apps/web`.

Internal styles are organized into separate files and imported into `globals.css`:

- `animations.css` - animations including accordion and toast
- `forms.css` - global form styles (including unset of chrome autofill styles)
- `palette.css` - custom palette tokens with `-P-` (palette) prefix with no coss/shadcn equivalent
- `shadcn.css` - coss-ui and shadcn/ui merged palette tokens (revised to use css `light-dark()`)
- `typeset.css` - typography styles generated by https://ui.shadcn.com/typeset
- `utilities.css` - custom utilities including `cx-focus-ring` to consolidate repeated focus ring styles

Third-party imports:

- `tw-animate-css` - shadcn and coss-ui dependency adds animation utilities
- `shadcn/tailwind.css` - shadcn/ui dependency adds custom tailwind variants and utilities

The `shadcn/tailwind.css` import covers the addition of `shimmer`, `scroll-fade`, `no-scrollbar`, custom `data-*` variants, etc.

## Palette Tokens

The palette tokens of coss-ui and shadcn/ui are merged into a single set of tokens and separate `:root` (light) and `.dark` (dark) colors are combined into single `light-dark()` definitions under `:root`.

See: [packages/ui/src/styles/shadcn.css](../packages/ui/src/styles/shadcn.css)

As coss-ui was inspired by shadcn/ui the tokens are almost completely compatible with the following exceptions:

- coss-ui additional status tokens for `info`, `success`, `warning`
- shadcn/ui `chart-*` tokens for charting and data visualization
- shadcn/ui latest versions do not have `destructive-foreground` (only `destructive`)

All coss-ui status tokens are a pair with background and `-foreground` tokens (including destructive).

The latest versions of shadcn/ui use only a single `destructive` token. Components use the opacity modifier to produce background and hover states from the single token (see the registry's button variants for an example).

To achieve consistency when using components from both coss-ui and shadcn/ui pay attention to `destructive` differences and any differences in border radius, padding, and spacing (which can vary depending on shadcn/ui preset).

### Light/Dark Theme

Theme (light/dark/system) is implemented using css `light-dark()` and `color-scheme`.

The benefit of this approach is that users automatically see their preferred theme (based on their system theme) without any effort or flicker. There is no need for client hints, javascript, or other workarounds.

The application implements a theme switch feature that enables users to override the system theme with a preferred theme which is persisted in a cookie.

In stylesheets:

- palette tokens are defined using single `light-dark()` instead of separate `:root` and `.dark`
- a custom tailwind `dark` variant is defined to support the use of `light-dark()` in tailwind classes
- the `color-scheme` property is set on the `:root` element to support system theme detection and automatic switching

## Class Merging Utilities

The popular `cn()` utility for merging tailwind classes may be imported from `@workspace/ui/lib/style`:

```ts
import { cn } from '@workspace/ui/lib/style'
```

The `cn()` utility combines `clsx` and `tailwind-merge` to support informed merging of tailwind classes.

The [packages/ui/src/lib/style.ts](../packages/ui/src/lib/style.ts) module builds on the shadcn boilerplate by scaffolding a custom `tailwind-merge` configuration via `extendTailwindMerge()`.

One of the primary reasons tailwind is not used to its full advantage is because custom variants and utilities are not supported by `tailwind-merge` out-of-the-box. The `extendTailwindMerge()` function enables you to add custom variants and utilities to the merge configuration so that they are properly merged.

## View Transitions

React's `<ViewTransition>` (React 19.3+) animates navigation. React Router runs navigations (`Link`, `NavLink`, `Form`,
`useNavigate()`, `useSubmit()`) in a React transition and React calls `document.startViewTransition()` for it.

See: [React Router view transitions](https://reactrouter.com/how-to/view-transitions) and
[React `<ViewTransition>`](https://react.dev/reference/react/ViewTransition)

`RouteTransition` ([apps/web/app/layout/route-transition.tsx](../apps/web/app/layout/route-transition.tsx)) wraps
`<Outlet />` in the root route. It is a `<ViewTransition>` keyed by `pathname`:

- a route change mounts a new boundary so the old page exits and the new page enters (`route` view transition class)
- `update="none"`: re-renders within the same route (pending UI, revalidation, search params, fetchers such as the
  theme form) start no view transition
- header, nav, and footer are outside the boundary and render live (not animated)
- keying remounts the page on a `pathname` change including a param change on the same route (`/posts/1` → `/posts/2`);
  pass `transitionKey` (e.g. the route id) to keep page state, and param changes then do not animate

The react-router docs show a persistent (unkeyed) boundary instead. Avoid that and any `update`/`default` animation on a
boundary that wraps router-driven content: React then starts a view transition for every transition commit inside it,
including the navigation's pending-state commit (and after hydration and on theme changes), and the route commit waits
for it to finish.

Rules:

- Do not use the deprecated react-router `viewTransition` prop/option, `useViewTransitionState()`, or `NavLink`
  `isTransitioning`/`.transitioning`: mixing them with `<ViewTransition>` can interrupt animations.
- Never call `document.startViewTransition()` by hand: React interrupts it.
- Keep React transitions on: no `useTransitions={false}` on `<HydratedRouter>` and no `flushSync` in navigations.
- Style with view transition classes (e.g. `::view-transition-old(.route)` in `globals.css`) rather than names.
- Shared elements: `<ViewTransition name="...">` on both sides with only one mounted per name at a time.
- Directional/typed animations: `addTransitionType()` inside `startTransition()` with the object form of the class props.
- Reduced motion is CSS-only (React does not handle it): see `globals.css`. Its rules need `!important` because
  `::view-transition-*(*)` has zero specificity and loses to `(root)` and `(.class)` selectors.
- Browser Back/Forward may not animate: React skips view transitions for synchronous `popstate` updates. It does animate
  when the route commit is async (as it currently is in `apps/web`), so do not rely on it either way.
- The root `ErrorBoundary` renders outside the boundary so leaving an error page does not animate.

View transitions must be considered in any UI/UX work, e.g. a modal or sheet opening or closing while the route changes.
